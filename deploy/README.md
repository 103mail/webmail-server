# Local deployment

Two Domains on one machine, separated the way the federation design describes:
each is its own Server with its own database, its own API process and its own
hostname, and neither can reach the other's data.

| | 103mail.com | example.com |
| --- | --- | --- |
| Hostname | `https://webmail.103mail.com` | `https://webmail.example.com` |
| Bound to | `127.0.0.1:443` | `127.0.0.2:443` |
| Login | `maurits@vdschee.nl` | `bob@example.com` |
| Password | `password` | `password` |
| Data | a dump of your local `webmail` database | generated fixtures |

Every account uses the password `password`, which is what `../../webmail/syncdata.sh`
sets on a synced database.

## What runs

```
                    ┌─ web-103mail (nginx) ──── 127.0.0.1:443
                    │     bundle, /config.json, peer descriptor, TLS
  dom-103mail ──────┼─ api-103mail (Go)
                    └─ db-103mail (MariaDB)

                    ┌─ web-example (nginx) ──── 127.0.0.2:443
  dom-example ──────┼─ api-example (Go)
                    └─ db-example (MariaDB)

  federation ─────── both web containers, aliased to their real federation
                     hostnames, plus both api containers and both workers
```

Per Domain there is also a `worker-*` container. It drains that Domain's
federation outbox and sweeps the state that ages out with it. It is separate
from the API because delivery to a peer has a 72-hour retry budget and cannot
sit behind a user's compose (ADR 17).

`dom-*` are internal networks, so a database is reachable only from its own
Domain's API. The `federation` network is the only thing the two share: each web
container carries `webmail.{domain}` as a network alias, so `api-103mail`
resolves `webmail.example.com` in the cluster exactly as it would on the
internet. That is the path federated envelopes actually travel.

One hostname serves the client bundle, `/config.json`, the peer descriptor and
the REST API, so the bundle and the API share an origin and there is no
cross-origin handshake between them. That is required, not incidental: RFC 4.1
roots every protocol endpoint at `webmail.{domain}` and permits no other
hostname.

## Setup

    ./setup.sh

Idempotent. It generates a local CA and a certificate per Federation hostname,
an Ed25519 keypair and federation config per Domain, the seed SQL, and the
attachment directories. Re-running keeps what exists, so the CA you trusted
stays trusted and pinned public keys do not move. `--reseed` rebuilds the seed
SQL.

Then, once:

1. Add to `/etc/hosts`:

       127.0.0.1  webmail.103mail.com
       127.0.0.2  webmail.example.com

   The whole of `127.0.0.0/8` is loopback on Linux, which is what lets both
   Domains have port 443 to themselves and keep URLs with no port suffix.

2. Trust `certs/webmail-local-ca.crt` in your browser. In Chrome that is
   Settings, Privacy and security, Security, Manage certificates, Authorities,
   Import. Firefox has its own store under Settings, Privacy & Security,
   Certificates, View Certificates, Authorities.

3. Bring it up:

       docker compose up -d --build

`docker compose down` stops it; `docker compose down -v` also drops the
databases, so the next start reseeds from scratch.

## Seed data

`seed/103mail.com.sql` is a data-only dump of whatever `webmail` database you
have locally, so the 103mail Domain comes up with real threads, calendars, chats
and attachments. `setup.sh` copies the attachment bytes out of
`../../webmail/data/attachments` to go with it; they are copied rather than
bind-mounted, because the stack writes new attachments and should not write into
the directory the PHP backend reads.

`seed/example.com.sql` is generated by `seed.sh` and holds one customer, one
user, a mailbox with its inbox and alias, a mail thread, three meetings around
today and a direct chat. That is enough for every section of the client to show
something. Edit `seed.sh` and re-run `./setup.sh --reseed`, not the SQL.

If you have no local `webmail` database, `setup.sh` falls back to generating the
same fixtures for 103mail.com too.

## Federation

It works. Composing from `bob@example.com` to `mevdschee@103mail.com` writes the
thread locally, returns to the browser immediately, and a worker carries the
signed envelope to the other Domain, which delivers it to the real mailbox. A
reply comes back onto the same thread on both sides. See ADR 17.

To watch it happen:

    docker compose exec db-example mariadb -uwebmail -pwebmail webmail \
      -e "SELECT peer_domain,status,attempts,last_http_status FROM federation_outbox"
    docker compose logs -f worker-example

Each Domain's keypair is in `keys/`, generated by `setup.sh` and never checked
in. `domain/{domain}/federation.json` names the key file and is checked in,
because it holds no key material. The peer descriptor at
`/.well-known/webmail-federation` is rendered by the server from the key it
actually signs with, so the two cannot drift apart.

Only the Basic tier of the protocol is implemented. The Registrar extension and
everything built on it (shadow mailboxes, real-email addressing) is not, and
these Domains advertise `"registrar": false`.

`/config.json` is still a static file per Domain: it is client branding, and the
backend has no opinion about it.

## What is not here

**Chat is polled, not pushed.** ADR 13 puts WebSockets in `../../ws2api`, which
converts a connection into `GET`, `POST` and `DELETE` on `/<ClientId>` against
the API server. `internal/api` routes none of those, so the proxy would refuse
every upgrade. `ws-103mail` and `ws-example` are defined behind the `chat-ws`
profile and do not start by default:

    docker compose --profile chat-ws up -d

The client polls every 5 seconds instead, in `useChats` and `useChatMessages`.
When the bridge lands, those two hooks are what changes.

**The certificates are not compliant.** RFC 9.2 requires a Web PKI certificate,
DV at minimum. These are signed by a local CA that only your machine trusts. A
peer implementing the RFC would refuse them, which is correct behaviour and not
a problem to work around locally.

**Email cannot leave.** No SNS or SES variables are set, so outbound
notifications are recorded in memory by `mailer.Recorder` and the inbound
webhook answers 503. The stack cannot mail a real person.

## Checking it works

    curl --cacert certs/webmail-local-ca.crt https://webmail.103mail.com/health
    curl --cacert certs/webmail-local-ca.crt https://webmail.example.com/.well-known/webmail-federation

To sign in with an API call rather than the browser:

    curl --cacert certs/webmail-local-ca.crt \
      -X POST https://webmail.example.com/api/v1/auth/token \
      -H 'Content-Type: application/json' \
      -d '{"email":"bob@example.com","password":"password"}'

## Running the client against a bare server instead

For frontend work, `npm run dev` in `../../webmail-client` is faster than a
rebuild. There is no backend on that origin to answer `/config.json`, so the
client falls back to a development config; point it at a locally running server:

    VITE_API_BASE=http://localhost:8080/api/v1 VITE_DOMAIN=103mail.com npm run dev

`http://localhost:5173` is already in the server's default
`WEBMAIL_ALLOWED_ORIGINS`.
